## Telegram-отправка (`abook-tg`, подключена 26.09)

CLI `~/.local/bin/abook-tg` (шебанг на `~/abook/.venv-tg/bin/python3` — там `telethon`+`cryptg`, системный python
их не видит) отправляет книги из библиотеки в личный Telegram-канал/группу пользователя через MTProto
(лимит файла 2 ГБ — Bot API с его 50 МБ не годится). Секреты: `~/abook/telegram.json` (api_id/api_hash/target,
chmod 600), сессия `~/abook/tg.session` (chmod 600), журнал отправленного `~/abook/tg-sent.json`. Временные тома
нарезки — `/mnt/d/VideoDownloader/Аудиокниги/.tg-tmp` (не в WSL). Команды: `setup [--target]`, `send <id|запрос>
[--dry-run] [--force] [--json-progress]`, `queue [N] [--profile ИМЯ] [--force] [--json-progress]`, `status`.

Интеграция в `abook review` (сервер на 8790, системный python — там telethon нет, поэтому реальная отправка всегда
идёт venv-подпроцессом `abook-tg … --json-progress`, сервер только читает построчный NDJSON с его stdout):
- `~/.local/bin/abook_tg.py` — тонкий мост, stdlib only, подключается в `abook` так же, как `abook_ai.py`
  (`try: import abook_tg as TG`). Функции: `configured()`, `target()`, `sent_summary()`, `sent_items()`
  (item_id → {complete, volumes, of, updated} — для кнопки «В Telegram» без похода за каждой книгой отдельно),
  `item_tg_state(item_id, has_file)`, `start_send(item_id, force)`, `start_queue(n, profile, force)`, `cancel()`,
  `job_status()`. Одна фоновая задача за раз (threading, subprocess.Popen), остальные запросы — в `_PENDING`
  и стартуют сами по завершении текущей.
- HTTP: `GET /api/tg/status` (job/target/sent_items), `POST /api/tg/send {item_id, force?}`,
  `POST /api/tg/queue {n, profile, force?}`, `POST /api/tg/cancel`.
- UI: одна переиспользуемая функция `tgBtn(it, small)` (в главном `<script>` `abook`, доступна и коду
  `abook_ai_ui.py`, т.к. это один и тот же скрипт после инъекции по маркеру `/*AI:JS*/`) — рисует кнопку по
  состоянию (не скачано / не настроено / идёт отправка k/n % / ✓ отправлено дата / отправить ещё раз) и живёт
  везде, где показана книга: карточка, поисковый дропдаун, «Мои отзывы», «Очередь», «Что дальше» (и
  детерминированный список, и закреплённый блок «Рекомендации ИИ»), «Библиотека» (таблица), результат анкеты
  (топ-5). Общий поллинг `pollTgNow()` — раз в 6 с, раз в 1,5 с пока идёт задача; строка статуса в
  «Экспорт» (`#tgInfo`) обновляется тем же тиком.
- Если `abook-tg setup` ещё не запускали — `configured()` вернёт `false`, кнопки показывают «не настроено»
  и подсказку запустить `abook-tg setup` в терминале; ничего не падает.
- Проверено (без реальной отправки в Telegram): `/api/tg/status` отдаёт реальный target пользователя (канал
  «books»), `/api/tg/send` с несуществующим id корректно ловит ошибку из подпроцесса и не роняет сервер,
  второй параллельный `send` встаёт в очередь (`queued:true`) и стартует сам после первого. Дальше пользователь
  сам сделал первую реальную отправку («Симулакрон-3», 3 тома) — видно в `~/abook/tg-sent.json`.

### Сжатие по умолчанию (добавлено тем же вечером)

Раньше том шёл `-c copy` как есть; теперь по умолчанию перекодируется в AAC — Telegram звук сам не сжимает.
Профили в `abook-tg` (`QUALITY_PROFILES`): `high` (по умолчанию, 80 кбит/с моно 44.1 кГц, ≈36 МБ/ч — рассчитан
на минимальную слышимую потерю от типичных ~128 кбит/с стерео источников), `speech` (64 кбит/с моно), `small`
(48 кбит/с моно), `original` (без перекодирования, как раньше). Кодек выбирается один раз за прогон
(`best_aac_encoder()`): `libfdk_aac`, если он собран в ffmpeg (на этой машине — нет), иначе нативный `aac`
с `-aac_coder twoloop`. `pick_effective_profile()` сравнивает битрейт/каналы исходника (`detect_source_audio()`,
через ffprobe) с целью профиля — если исходник и так не хуже (битрейт ≤ цели·1.05 и каналов не больше), том
идёт как есть без перекодирования, даже если запрошено сжатие. Кодирование — `nice -n 10`, прогресс читается
из `ffmpeg -progress pipe:1` (поле `out_time_ms` там на самом деле в микросекундах — особенность ffmpeg) и
шлётся в NDJSON как событие `encode_progress`; в `abook_tg.py` это ложится в `job.volume.stage="encode"`
(было только `"upload"` через событие `progress`), кнопка в UI показывает «⏳ k/n %» на стадии сжатия и
«✈ k/n %» на стадии отправки. Профиль по умолчанию хранится в `telegram.json` (несекретный ключ `quality`),
меняется через `abook-tg send --quality …` разово или через `POST /api/tg/quality {quality}` — селектор
«Качество сжатия по умолчанию» в «Экспорт», значения `TG_QLABEL` в JS.

Раздельно поменялось и правило нарезки на тома (по просьбе пользователя, не связано напрямую со сжатием):
было «>4 ч или >1,9 ГБ → тома 2,5–3,5 ч», стало «>8 ч (или неизбежный останов по 1,9 ГБ) → тома 4–6 ч»
(`CAP_DUR`, `TARGET_VOL_DUR`, `MIN_VOL_DUR`, `MAX_VOL_DUR` в `abook-tg`). С компрессией по размеру дробить
почти никогда не приходится раньше правила по длительности (65+ ч ушло бы в 1,9 ГБ даже на 64 кбит/с).

Проверено: encode одного 3-часового тома «Война и мир» на `high` — длительность на выходе 10800.000000 с
(0 с расхождения), `ffmpeg -v error -f null -` decode чисто, размер 113 МБ (нативный `aac` даёт чуть выше
номинала: ~82 кбит/с фактических при цели 80). Профиль `small` на синтетическом моно-48к исходнике корректно

### TG-очередь, проверка полноты перед отправкой, переотправка (30.09)

`abook_tg.py` переписан вокруг явной **TG-очереди** `~/abook/tg-queue.json` (атомарная запись tmp→replace;
`_PENDING` в памяти убран). Запись: `item_id, title, author, force, skip_check, state, added/started/finished,
message, warn, check, resumed, pid`; состояния `queued → checking → sending → done | problem | error | cancelled |
dry_run`, завершённых хранится до 30 (для пометок). Один воркер-поток берёт первую `queued`. При старте сервера
(`TG.resume()` в `cmd_review`) прерванные `checking/sending` снова встают в очередь (`resumed`), а переживший
сервер подпроцесс (pid записан в запись, своя группа процессов) прибивается — чтобы не было двух отправок одной
книги; `queued`, уже полностью отмеченные в `tg-sent.json` (и не переотправка), сразу становятся `done`.
`force` снимается с записи на первом `volume_start` (abook-tg к этому моменту уже убрал старую запись журнала),
поэтому после перезапуска посреди переотправки продолжение идёт докачкой, а не новым `--force`.

**Проверка полноты перед каждой книгой** (одиночной и из очереди) — в мосте, до запуска `abook-tg`:
свежий отчёт `~/abook/check-reports/<id>.json` берётся без запуска, если совпадают путь, sha256 из state и
`file_size`/`file_mtime` (их теперь пишет `abook-check`; у старых отчётов — «файл не новее `checked_at`»).
Иначе `abook-check <id> --json --timeout 780` (общий таймаут `ABOOK_CHECK_TIMEOUT`, 900 с), фазы из его stderr
(«распознавание речи…», «спрашиваю Claude…») идут в UI. Вердикт `incomplete / wrong_order / wrong_work` →
книга **не** отправляется, `state=problem` с `summary_ru`, очередь идёт дальше; «всё равно отправить» =
`POST /api/tg/send {item_id, skip_check:true}`. Любой сбой проверки (нет `claude` в PATH, ненулевой код —
лимит/ошибка Claude/упал whisper-venv, таймаут, не-JSON) → `warn` «проверка недоступна: …, отправляю без неё»
и отправка продолжается. Отмена (`/api/tg/remove` для текущей, `/api/tg/cancel` = «остановить всё») убивает
группу процессов — и проверку, и abook-tg с ffmpeg.

**Переотправка:** `send --force` больше не выбрасывает старую запись журнала, а переносит её в
`tg-sent.json → superseded[item_id]` (id старых сообщений; сводки/кнопки считают только `items`). Старые
сообщения в канале остаются; опционально `abook-tg send <id> --force --delete-old` удаляет их после успешной
полной переотправки (по умолчанию выключено, из UI не вызывается).

HTTP: `POST /api/tg/send {item_id, force?, skip_check?}` (ставит в очередь; стартует сразу, если пусто),
`POST /api/tg/remove {item_id}` (убрать из очереди / прервать текущую / снять пометку), `/api/tg/cancel`,
`GET /api/tg/status` (+ `queue` с `position`, `check_phase`, `volume` у текущей; `sent_items[].superseded`).
UI: кнопка `tgBtn` — «✈ в Telegram» → «✈ TG-очередь · №k» → «✈ проверка…» → «✈ сжатие k/n %» →
«✈ отправка k/n %» → «✓ в Telegram»; «⚠ проверка: проблема», «✈ ошибка»; у отправленных томами —
«✓ в Telegram · 3 тома», клик → подтверждение «Переслать одним файлом?» (`confirmDlg`, 4-й аргумент `'plain'` —

**yt-dlp без скачивания** (`-J`, плейлист `--flat-playlist`; archive.org — metadata API, MP3 одной группы по
порядку + HEAD первого файла; части-ссылки — каждая): доступность, длительность, число частей, пропуски, порядок

вариант близок по баллам и отличается чтецом/видом/языком, или лучший «короче ожидаемого», или названный чтец не
совпал. Уже есть в библиотеке — `library_match` (same_book): скачано / качается / в каталоге (тогда «Скачать эту
запись» = `enqueue_catalog`: её собственная запись из её манифеста). kind=prompt → UI сам отдаёт текст консультанту.
«Скачать» у совета консультанта вне библиотеки = поиск с `auto:true`: однозначный лучший вариант ставится в загрузки

(формат обычных манифестов, раздел по выбору Claude из существующих или «Открытия/По запросу»,
«Аудиоспектакли/По запросу» для радиоспектаклей; в манифесте только скачанное и качающееся) → `abook get

сервера загрузку не обрывает; новый сервер находит живой pid и дочитывает лог). Прогресс: части k/n по логу,
% внутри части — размер staging против ~128 кбит/с. Состояния queued → downloading → merging → checking → done |
error | cancelled. После скачивания `abook-check <id> --json` (нет claude — предупреждение, без проверки),
затем `sync_db` + файлы для ИИ. Отмена = SIGTERM группе; отменённое/неудачное убирается из ui-requests.json,

**Карта связей** (`abook_links.py`): признаки — темы, идеи, мотивы, тон, приём, «цепляет», герой, масштаб + жанр,

## Векторы, гибридный поиск, вкус, RAG консультанта (01.10, этап 2 п. 3–5)

Код: `abook_vec.py` (один файл, два режима). Сервер (stdlib) строит тексты, FTS, RRF и вкус. Демон
`abook_vec.py --daemon` запускается лениво из venv `~/abook/.venv-vec` (fastembed + onnxruntime + numpy, `uv`),
общается JSON-строками по stdin/stdout. Операции: `hello`, `sync`, `embed`, `search`, `mix`, `scores`. Сервер умер —
у демона EOF на stdin, он выходит сам. Нет venv или `ABOOK_VEC=0` — гибрид работает только по FTS, вкуса нет,
консультант получает кандидатов без векторов, ошибок нет. Демон упал — 1–10 мин не перезапускается.

**Модель** — `intfloat/multilingual-e5-small` (384 изм., ONNX через `add_custom_model`, префиксы `query:`/`passage:`).
Модель лежит в `~/abook/.venv-vec/models`. На 20 смысловых запросах по аннотациям библиотеки: e5-small hit@10 —
18/20, MRR 0,59; `paraphrase-multilingual-MiniLM-L12-v2` — 15/20, MRR 0,50. Векторы считаются на CPU с 16 потоками;
onnxruntime-gpu потребовал бы ≈ 2 ГБ CUDA-библиотек. Размер venv ≈ 650 МБ, из них модель 465 МБ.

**Скорость**: книги с аннотацией (≈ 210 символов) — ≈ 45–50 в секунду, короткие записи каталога — ≈ 165 в секунду.
Полный первый расчёт на 1,6 тыс. записей занял 38 с и идёт в фоне демона. Старт демона с загрузкой модели — 3–4 с.
Вектор запроса — ≈ 6–28 мс, перебор 200 тыс. × 384 — ≈ 22 мс (argpartition). `/api/find/hybrid` — 35–100 мс,
`/api/find/foryou` — ≈ 190 мс.

**Таблица** `vec_items(kind item|src|work, ref_id, model, sig, blob float16)` создаётся демоном. sig — хэш текста.
`ensure_sync` сверяет таблицу не чаще раза в 5 минут или при смене count/max(rowid) в items/src_items/works/
book_features: новое и изменённое досчитывается, исчезнувшее удаляется. Индекс: 768 байт на запись,
1,5 МБ на 2,5 тыс. записей.
Текст вектора: «автор — название. чтец. аннотация (about/note). признаки карты связей». Для src_items:
`_tidy` срезает эмодзи и рубрики вида «📘[SCI-FI]», записи без автора (анонсы, стримы) не индексируются,
members не индексируются. `works` индексируется, если таблица есть (id, author, title, annotation|about).

**Гибрид** `hybrid(q, k, scope library|catalog|all)` = RRF (k = 60) из трёх списков:
- FTS библиотеки (`items_fts`): сначала совпадение всех слов, затем добор «хоть одно слово» с весом 0,5;
- FTS каталога (`abook_catalog._fts`);
- векторы.

`GET /api/find/hybrid?q=&scope=&k=` → `{q, scope, k, vec, ms, items:[карточка, rrf, fts, vec, sim, taste]}`. Карточка
src: `id="s<id>"`, `src_key` (= source_id для `POST /api/find/download {catalog_key}`), url, platform, availability.
Роутинг — в `abook_links.handle_get` (/api/find/hybrid, /api/find/foryou, /api/find/vec/status).

**Вкус**: `taste_vector` = Σ ((оценка − средняя)/5 · вес свежести `A.review_weights`) · v(книга). «Бросил» — не
выше −0,4. Анкета добавляет понравилось (+) и не понравилось (−). Книга вне библиотеки встраивается текстом
«автор — название». Кэш по составу отзывов — 1 ч. `taste_scores` — косинус с вектором вкуса для любых записей.
`GET /api/find/foryou?k=` — каталог источников, только public/unknown и downloadable, без знакомого и без того,
что есть в библиотеке, одна строка на книгу.

**RAG консультанта** (`abook_links.rag_context`, `abook_vec.rag_candidates`). Вместо §5 CATALOG и §7 INDEX
lite-файла в промпт идёт блок «КАНДИДАТЫ» — `ABOOK_CHAT_CANDS`, по умолчанию 40; 0 — по-старому. Состав:

- если всё равно мало — скачанное без отзыва.

Строка: `id | автор — название | ч | чтец | пометки (нет на диске/не скачано) | признаки или начало аннотации |
откуда`. Профиль, анкета, отзывы, §2a и §5b остаются. `validate_recs` принимает `s<id>` и совпадение по названию

## Модель вкуса и ранжирование (01.10, этап 2: вкус, качество, двухэтапный отбор)

Код: `abook_rank.py` (новый, stdlib), операция демона `rank` и фоновая сверка в `abook_vec.py`, в `abook_links.py` —
маршруты `/api/find/feedback`, сводка «МОДЕЛЬ ВКУСА» и реакции «читал» в `build_chat_prompt`. Абзацы выше про
`taste_vector`, `foryou` и состав RAG описывают прежнее поведение: теперь всё идёт через `abook_rank.rank`.

**Почему.** В живой базе 6 профилей, у всех анкета и профиль от ИИ, а отзывов 0. Старый вкус строился из отзывов
и книг анкеты одним средним вектором, поэтому вкуса фактически не было. Кроме того, каталог источников на 96 %
состоит из archive.org: там веб-романы без автора, музыка, проповеди, «Voice of Korea». Похожесть на теги вкуса
без сигнала качества выносила наверх именно их.

**Сигналы профиля** (`signals`, кэш `profile` по составу анкеты, ai_runs, памяти, реакций и отзывов):

| Сигнал | Вес | Как используется |
|---|---|---|
| Профиль ИИ: «любите» | +1,0 | Каждый тег — отдельный текстовый сигнал и кандидат в грань. |
| Профиль ИИ: «лучше избегать» | −0,8 | Голос и длина идут не в вектор, а в реранк. |
| Профиль ИИ: оси вкуса | +0,35 | |
| Анкета: книги | ±(0,3…1,1) по оценке | Книга, которая есть в библиотеке или каталоге (`_book_key`: скелет названия и автор, как в `abook_catalog`), берётся вектором записи с аннотацией, иначе — текстом. |
| Анкета: `kind="author"` | ±1 | Любимый или нелюбимый автор: текст «книги автора X. why» и родство по автору. |
| Анкета: фильмы, сериалы, игры, жанры, интересы | +0,12…0,35 | Тексты. |
| Анкета: `extra.text` и `qa` | +0,4 / +0,25 | |
| Анкета: `extra.avoid_topics` | −0,8 | |
| Бриф «Основного» | +0,45 | По предложениям, без строки «Уже прочитано». |
| Отзывы | (оценка − средняя) × свежесть | «Бросил» — минус. |
| Память консультанта | вкус +0,5, «не нравится» −0,6, «не интересно» −0,3 | «Не интересно» ещё и исключается. |
| Реакции `rec_feedback` | like +0,8, dislike −0,8 | `read` — только в «уже знакомо». |

**Жёсткие фильтры:**
- `extra.avoid_authors`;
- «уже знакомо»: книги анкеты, отзывы, бриф, реакции read и dislike, «не интересно»;
- «відьмак, всі томи» означает, что знаком весь цикл: совпадение по первому слову названия и автору;
- записи «только для спонсоров» и нескачиваемые;
- `_irrelevant`: игровые визуализации, трейлеры, обзоры, музыка, стримы, подкасты; записи короче 10 минут;
  записи без автора, у которых в названии меньше 4 букв или аннотация короче 60 символов;
- «свои» и «уже прочитано» (`in_library=0`) — это заметки, а не книги для совета.

**Родство по автору** (`_author_affinity`). Сравниваются первые 5 букв фамилии после `fold`, поэтому совпадают
«Сапковський» и «Сапковский», «бредберри» и «Брэдбери». Веса: любимый автор +1, автор понравившейся книги +0,5,
автор отзыва ≥ 8 — +0,4, нелюбимый автор −1. Все произведения любимых авторов попадают в recall.

**Языки** — `abook_ai.lang_weights` (по умолчанию ru = uk = 15, en = 3). Балл записи равен весу её языка,
делённому на максимум. Если английский «немного», в выдаче не больше 1 английской книги из 5.

**Демон, операция `rank`.** Положительные сигналы собираются в 2–6 граней: взвешенный k-means по косинусу,
K ≈ √n, начальные центры выбираются по дальности, начиная с самого весомого сигнала. Для каждой записи считается
z-оценка близости к каждой грани и к каждому отдельному сигналу. Оценки — по всем записям выбранных kinds, чтобы
грани были сравнимы. Из близости сначала вычитается «хабовость» записи (средняя близость к 512 случайным записям,
поправка как в CSLS): короткие шаблонные тексты вида «Аудиокнига-Триллер "…"» иначе близки ко всему.
Демон возвращает:
- `taste` = лучшая грань × (0,5 + 0,5 · вес грани) + 0,2 · средневзвешенное по граням;
- `knn` = среднее двух лучших отдельных сигналов;
- `neg` = ближайший «не моё»;
- номер грани.

Векторы текстов-сигналов кэшируются в демоне. Подпись грани в выдаче (`facet_label`) — 1–3 самых весомых
словесных сигнала.

**Отбор** (`rank(conn, pid, text, k, mode)`), mode = `foryou` (только нескачанное) | `rag` | `eval`.

1. Recall, ≈ 700–900 записей:
   - топ-600 по вкусу во всём индексе (item, work, src);
   - гибрид по запросу, 80 записей;
   - мосты карты связей;
   - 300 самых известных записей канона;
   - все произведения любимых авторов.

   src с произведением сворачивается в произведение.
2. Реранк. «Личное» = вкус + 0,3·kNN − 0,5·«не моё» + 1,2·запрос + 0,3·мост + 0,25·автор. Оно умножается на
   «ворота» качества: 0,5 + 0,5·min(1, q/0,85). К результату прибавляются:
   - 0,5·q;
   - доступность 0,1;
   - полнота записи 0,08;
   - язык 0,12;
   - длительность 0,12 (по `extra.hours`, `prefs.length` или «как вы слушаете» ИИ);
   - тон 0,1 (`extra.darkness` против «мрачных» и «светлых» слов аннотации; «перед сном» — штраф резкому);
   - карточка 0,8 (есть автор, часы, аннотация).

   Вычитаются «не книга» (0,6) и ИИ-голос (0,15, если профиль его избегает).
3. Одна строка на книгу: скелет названия и пересечение автора.
4. Разнообразие: из одной грани не больше трети выдачи, не больше 2 книг одного автора, английских — с ограничением.

Для `rag` произведение превращается в карточку лучшей записи (`s<id>`): так его принимает `validate_recs`, а
скачивается оно через `{catalog_key: src_key}`. Каталога не больше половины, остальное — книги библиотеки.
Строка кандидата получает «★», если это канон Wikidata или у записи высокий сглаженный рейтинг. Поле «откуда» —
«запрос», «мост» или «вкус: <грань>».

q = 0,12 + 0,45·канон + 0,12·популярность + 0,31·сглаженный рейтинг (без рейтинга — 0,42), затем умножается
на «книжность» записи:
- 1 — теги «аудиокнига», «librivox», жанры или YouTube-канал;
- 0,25 — музыка, лекции, проповеди, новости;
- 0,55 — без тегов;
- × 0,6 — короче 10 минут.

Рейтинги дозапрашиваются лениво: после каждой выдачи — не больше 20 запросов для её топа, ≈ 1 запрос/с, не чаще
раза в 2 минуты. Промах тоже кэшируется на 30 дней. Прогрев — `python3 abook_rank.py ratings --limit 400`.
Канон — `python3 abook_rank.py canon` (QLever, при неудаче WDQS, затем `match_canon`); после роста каталога
достаточно `python3 abook_rank.py match`.

**Признаки карты связей для нескачанных** (`feature_batch`). Работают в фоне, не чаще `ABOOK_RANK_FEAT_GAP`
(600 с): одна пачка до 25 произведений — та же `_feat_prompt` и Sonnet, что в `abook_links`. Признаки пишутся в
`book_features` с id `w<id>`. Сначала берутся произведения, которые попадали в выдачу ≥ 2 раз (`rank_hits`),
добор — из текущего топа. Признаки попадают в текст вектора произведения и в «мост» реранка (`_bridge_scores`:
связь с любимыми книгами, у которых есть признаки). Проверено одной реальной пачкой: 25 из 25 книг получили
признаки (≈ $0,1). `ABOOK_RANK_FEATS=0` — выключить, `ABOOK_RANK_NET=0` — без сети.

**Сверка векторов** (`abook_vec.ensure_sync`) теперь идёт фоном. Разницу считает сервер: демону уходят только
новые и изменённые тексты и удалённые ключи (операция `sync2`). Полный `docs()` на 57 тыс. записей занимает ≈ 5 с,
и раньше раз в 5 минут блокировал запрос. Сверка запускается при смене состава таблиц или раз в 30 минут.
Матрица демона читается одним `frombuffer`. **На живой базе `vec_items` ещё нет:** первый запрос запустит в
демоне расчёт 57 тыс. векторов. На копии это заняло ≈ 38 мин при 18–23 записях/с под нагрузкой машины. Пока
расчёт идёт, «для вас» работает по уже посчитанному.

**HTTP:**
- `GET /api/find/foryou?k=20&q=` → `{items:[{kind, ref, id (w<id> | item id), src_key, author, title, reader,
  hours, lang, platform, url, availability, about, score, parts, quality, facet_label}], facets, pool, ms}`.
  Скачать: `POST /api/find/download {catalog_key: src_key}`, для книги библиотеки — `{item_id}`.
- `POST /api/find/feedback {verdict: like|dislike|read, author, title, item_id?, src_key?}` → `{ok, verdict}`;
  400, если verdict другой или нет ни title, ни item_id, ни src_key. Повторная реакция на ту же книгу (по item_id,
  src_key или same_book) заменяет прежнюю. Вкус пересчитывается на следующем запросе.
- `GET /api/find/feedback` → `{items:[…]}`.
- `GET /api/find/quality/status` → `{canon, by_source}`.

**Офлайн-оценка** (leave-one-out, копия живой базы, 57 тыс. векторов). Для каждой понравившейся книги анкеты
(у «Основного» — «Уже прочитано» брифа) книга прячется: из анкеты, из «знакомого», из текста брифа и профиля ИИ.
